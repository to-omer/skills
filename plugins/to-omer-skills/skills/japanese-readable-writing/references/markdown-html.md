# MarkdownとHTMLで文書構造を表す

MarkdownやHTMLへ変換するときは、原文の見た目をそのまま写さない。内容を読み取り、題名、節、段落、リスト、表、注記などの役割に分けてから、出力形式に合う構文や要素を選ぶ。

## 変換の基本手順

1. 原文を、意味のまとまりごとに分ける。
2. 各部分が何のためにあるか判断する。
   - 題名、要点、節、段落、手順、比較、引用、注記など。
3. 情報の親子関係と読み順を整理する。
4. 出力先が対応している構文やHTML要素を選ぶ。
5. 表示結果とソースの両方を確認する。

フォントサイズ、太字、字下げ、改行は、構造を判断する手掛かりにすぎない。大きな文字が必ず見出しとは限らず、字下げされた文章が必ずリストとは限らない。

## 変換前に見分ける要素

原文を、次のような要素に分ける。

- 文書の題名
- 冒頭の要約
- 節と小節
- 段落
- 並列項目
- 手順
- 用語と説明
- 比較表
- 条件表、判断表
- 引用
- コード、コマンド、出力
- 注記、注意、警告
- リンクと参照先
- 図、画像、キャプション
- 日付、著者、版などのメタデータ

原文の構造が曖昧な場合は、表示だけを根拠に決めない。文脈からも決められなければ、確認事項として残す。

## 内容上の役割と形式を対応させる

| 内容上の役割 | Markdown | HTML | 注意点 |
|---|---|---|---|
| 文書の題名 | `#` | `<h1>` | ページの主題を示す |
| 節、小節 | `##` 以降 | `<section>` と見出し | 階層を飛ばさない |
| 段落 | 空行で区切る | `<p>` | 改行だけで段落にしない |
| 並列項目 | `-` | `<ul><li>` | 同じ階層の項目を並べる |
| 手順、順位 | `1.` | `<ol><li>` | 順序に意味がある場合だけ使う |
| 用語と説明 | 見出しと段落、表、対応する拡張構文 | `<dl><dt><dd>` | CommonMarkには説明リストがない |
| 引用 | `>` | `<blockquote>` | 注記の装飾に流用しない |
| インラインコード | バッククォート | `<code>` | UIラベルとコードを区別する |
| 複数行のコード | コードフェンス | `<pre><code>` | 可能であれば言語名を付ける |
| 比較データ | 対応環境なら表 | `<table>` | 見出しと値の関係を示す |
| 画像 | `![代替テキスト](URL)` | `<img alt="...">` | 画像の目的に合う代替テキストを書く |
| 図と説明 | 実装依存、HTML埋め込み | `<figure><figcaption>` | Markdown標準には専用構文がない |
| 補足、注意 | ラベル付き引用など | 見出しまたはラベルを付けたまとまり | 色やアイコンだけに頼らない |
| リンク | `[目的が分かる文言](URL)` | `<a href="...">` | `こちら`だけにしない |
| 操作 | Markdownだけでは表せない場合がある | `<button>` | 移動はリンク、実行はボタン |
| 日時 | 通常の文章 | `<time datetime="...">` | 表示値と機械可読値を分けられる |
| 振り仮名 | HTML埋め込みなど | `<ruby><rt>` | 出力先の対応を確認する |

## Markdownで使える構文を確認する

Markdownには実装ごとの差がある。出力先が不明な場合は、CommonMarkで広く使える構文を基本にする。

### 広く使える構文

- `#` を使う見出し
- 段落
- 箇条書き
- 番号付きリスト
- 引用
- 強調
- リンクと画像
- インラインコード
- コードフェンス

### 出力先の確認が必要な構文

- 表
- タスクリスト
- 取り消し線
- 脚注
- 定義リスト
- callout、admonition
- wiki link
- Mermaid
- 数式
- フロントマター（front matter）の独自項目

対応していない構文を使うと、記号がそのまま表示されたり、情報の関係が失われたりする。必要であれば、通常の見出し、段落、リストで代替できる形も用意する。

## Markdownの見出し

- 文書の題名には、原則として `#` を一つ使う。
- 大きな節は `##`、その中の小節は `###` と、一段ずつ下げる。
- 文字を小さく見せるために、見出しレベルを選ばない。
- `##` の直下に `####` を置かない。
- 見出しには、その節の対象か問いを書く。
- 見出し行に、長い説明、複数のリンク、過剰な強調を入れない。
- 見出しを変更するとアンカーURLが変わる環境では、既存リンクへの影響を確認する。

不適切な例:

```markdown
**申請方法**

#### 必要書類
```

改善例:

```markdown
## 申請方法

### 必要な書類
```

## Markdownの段落と改行

- 段落は空行で分ける。
- エディタ上の折り返しを、意味のある改行と見なさない。
- `<br>` や行末の空白による強制改行は、複数行の住所や詩など、改行自体に意味がある場合だけ使う。
- 空行を重ねて余白を作らない。
- 原文の改ページを、そのままWeb上の節の区切りにしない。

## Markdownのリスト

### 同じ階層に並べる項目

同じ字下げの項目は、同じ種類、同じ視点、同じ程度の細かさにする。

不統一な例:

```markdown
- 管理者の承認
- 申請書を提出する
- 本人確認済みであること
```

改善例:

```markdown
- 管理者の承認を受ける。
- 申請書を提出する。
- 本人確認を完了する。
```

### 従属する情報

上位項目だけに関係する条件、例外、例、補足は、一段下げる。

```markdown
- 通常申請
  - 上長の事前承認が必要です。
- 緊急申請
  - 事後承認でも構いません。
  - 申請理由を添えてください。
```

条件がリスト全体にかかる場合は、リストの前に書く。一つの項目だけにかかる場合は、その項目の下に置く。

### 番号付きリスト

番号を使うのは、次の場合に限る。

- 実行する順番がある。
- 優先順位がある。
- 件数が重要である。
- 後から番号で参照する。

単なる並列項目には、箇条書きを使う。見出しへ手作業で番号を付ける場合も、手順を示したり後から参照したりするために番号が必要か確認する。

### 深い入れ子

三段以上の入れ子は避ける。関係が複雑な場合は、見出しや判断表に分けるか、手順を分割する。

## Markdownのチェックリスト

`- [ ]` は、作業や確認の完了状態を示すときに使う。

適切な例:

```markdown
- [ ] 申請書を記入した。
- [ ] 本人確認書類を添付した。
- [ ] 上長の承認を受けた。
```

説明、特徴、参考情報をチェックリストにしない。閲覧環境によっては、チェック操作ができず、静的な表示になる点にも注意する。

## Markdownの表

Markdownの表は、CommonMarkの中核構文ではない。出力先が対応している場合だけ使う。

Markdownの表に向いているのは、次のような内容である。

- 行と列の意味が明確である。
- 同じ項目を同じ軸で比べる。
- セル内の情報が短い。
- 結合セルを必要としない。

Markdownの表に入れない方がよいのは、次のような内容である。

- 複数段落や長いリストをセルに入れる。
- 空欄、該当なし、未確認を同じ空セルで表す。
- 罫線だけで重要な階層や順序を示す。
- 小さな画面で読めないほど列を増やす。

複雑な表は、HTMLの表、候補ごとの節、見出し付きリストなどへ変える。

## Markdownのコード

- コード、コマンド、ファイル名、パス、設定値、キー名は、必要に応じてバッククォートで囲む。
- 複数行のコードは、コードフェンスで囲む。
- 可能であれば言語名を付ける。
- コード内の字下げ、改行、記号を文章校正で変えない。
- コマンドと実行結果を分ける。
- プレースホルダーは、実際の値と見分けられるようにする。
- 秘密情報や実在する認証情報を例に入れない。

````markdown
```bash
example-command --input <file>
```
````

## Markdownのリンク

リンク文だけで、移動先や目的が分かるようにする。

- 弱い: `[こちら](...)`
- 改善: `[申請書の記入例を確認する](...)`

同じリンク文を、異なる移動先に使わない。URLそのものを見せる必要がなければ、意味のあるリンク文にする。

## Markdownの強調と装飾

- 太字は、読み落とすと誤解や作業ミスにつながる短い箇所に使う。
- 段落全体を太字にしない。
- 見出しの代わりに太字を使わない。
- 太字だけで、必須、任意、警告を区別しない。ラベルや文章でも示す。
- 日本語の長い斜体は、読みにくくなることがあるため避ける。
- 装飾目的の絵文字、罫線、記号を増やさない。
- 日本語の地の文では、全角ダッシュ、長い中黒の並列、不要な引用符を多用しない。

## Markdownの引用と注記

引用は、他者の文章や原文を示すために使う。

注記として引用構文を使う場合は、役割を言葉で示す。

```markdown
> **補足:** この設定は、新しく作成するアカウントにだけ適用されます。
```

製品固有のcallout構文を使う場合も、装飾が表示されなくても意味が通る文章にする。

## Markdownの画像

- 代替テキストには、文脈の中で画像が伝える情報を書く。
- 画像の外観を無目的に列挙しない。
- 周辺の本文と同じ説明を重ねない。
- 装飾画像は、対応する環境で空の代替テキストにする。
- 図の結論は、本文にも書く。
- 画像がリンクになっている場合は、リンク先の目的も分かる代替テキストにする。

## Markdownのメタデータ

フロントマター（front matter）はMarkdown標準ではない。使う場合は、出力先の仕様に従う。

- 必要な本文情報を、front matterだけに置かない。
- 日付は、解釈が一つに定まる形式にする。
- タイトルをフロントマターと本文の両方で管理する場合は、不一致を防ぐ。
- 独自項目を作る前に、出力先のスキーマを確認する。

## HTML文書の基本構造

ページ全体を作る場合は、次を確認する。

- `<!doctype html>` を使う。
- `<html lang="ja">` で主な言語を示す。
- `<meta charset="utf-8">` を早い位置に置く。
- `<title>` に、タブや検索結果で識別できるページ名を書く。
- ページの主題を、原則として一つの `<h1>` で示す。
- 主要な内容を `<main>` に置く。
- 単独でも内容が成り立つまとまりは、必要に応じて `<article>` にする。
- 見出しで表せる主題ごとのまとまりは、必要に応じて `<section>` にする。
- ナビゲーションは `<nav>`、補足的な内容は `<aside>` を検討する。
- 意味に合う要素がない場合に限り、`<div>` を使う。

## HTMLの見出し

- `<h1>` から `<h6>` は、内容の階層を表す。
- 文字サイズを変える目的で見出しレベルを選ばない。
- 下位の節へ進むときに、レベルを飛ばさない。
- 上位の節へ戻ることは問題ない。
- `<section>` を使う場合は、通常、その内容を説明する見出しを付ける。
- 画面には表示しない見出しを、理由なく増やさない。

## HTMLの段落、リスト、説明リスト

- 通常の文章は `<p>` にする。
- 順序のない一覧は `<ul>`、順序のある一覧は `<ol>` にする。
- 用語と説明、名前と値の組には、必要に応じて `<dl>`、`<dt>`、`<dd>` を使う。
- 空の `<p>` や、連続する `<br>` で余白を作らない。
- レイアウトのためにリストを使う場合も、内容が実際に一覧であるか確認する。

## HTMLの表

`<table>` は、行と列で表すデータに使う。ページのレイアウトには使わない。

- 表の目的を `<caption>` で示す。
- 列見出しと行見出しを `<th>` にする。
- 単純な表では、`scope="col"` または `scope="row"` を使う。
- データは `<td>` にする。
- 複雑な見出しを持つ表では、必要に応じて `id` と `headers` で関係を示す。
- 小さな画面でカード表示に変える場合も、見出しと値の関係をDOM上で保つ。

例:

```html
<table>
  <caption>プラン別のログ保存期間</caption>
  <thead>
    <tr>
      <th scope="col">項目</th>
      <th scope="col">基本プラン</th>
      <th scope="col">上位プラン</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">保存期間</th>
      <td>30日</td>
      <td>365日</td>
    </tr>
  </tbody>
</table>
```

## HTMLのリンクとボタン

- 別の場所へ移動する場合は、`<a>` を使う。
- 現在のページで処理を実行したり、状態を変えたりする場合は、`<button>` を使う。
- リンク文は移動先を、ボタン文は実行する操作を示す。
- `こちら`、`詳しく`、`実行` だけにしない。
- 見た目だけリンクやボタンにした `<div>` や `<span>` を使わない。
- リンクを開くと新しいウィンドウへ移る、PDFを開く、またはファイルをダウンロードすることが重要なら、リンク文や補足で伝える。

## HTMLのコードと技術情報

- インラインコードは `<code>` にする。
- 複数行のコードは `<pre><code>` にする。
- 変数名には `<var>`、出力例には `<samp>`、キーボード入力には `<kbd>` を必要に応じて使う。
- コードの違いを、色だけで示さない。

## HTMLの日時、略語、振り仮名

- 日時を機械でも解釈できるようにする場合は、`<time datetime="...">` を使う。
- 略語は本文で初出時に説明し、必要に応じて `<abbr>` を使う。
  - `title` 属性だけに説明を置かない。
- 振り仮名には `<ruby>` と `<rt>` を使う。
- 用語の定義には、必要に応じて `<dfn>` を使う。
  - 周辺の文章でも、何を定義しているか分かるようにする。

## HTMLの画像と図

- 情報を伝える画像には、目的に合う `alt` を付ける。
- 装飾画像には `alt=""` を付ける。
- キャプションのある図は、`<figure>` と `<figcaption>` を使う。
- 複雑な図やグラフには、要点と詳しい説明を本文にも用意する。
- 通常の本文を、文字だけの画像で置き換えない。

## HTMLの注記と警告

HTMLには、あらゆる警告に使える専用要素はない。

- 見出しやラベルで、補足、注意、警告などの役割を示す。
- 内容に合う場合は `<aside>` を使えるが、本文の主要な条件を脇の情報として扱わない。
- ARIAを追加する前に、適切なHTML要素を使う。
- `role="alert"` は、動的に発生し、すぐ知らせる必要がある内容に限る。
  - 静的な注意書きへ乱用しない。

## DOMの順序と見た目の順序

- CSSが適用されなくても意味が通る順に、HTMLを並べる。
- CSS GridやFlexboxで見た目だけ順序を入れ替え、読み上げ順と食い違わせない。
- 重要な注意が手順の前に必要なら、DOM上でも手順より前に置く。
- 色、位置、形、大きさだけで指示しない。
- 画面を拡大した場合や、文字間隔・行間を変更した場合、狭い画面で表示した場合にも、情報や操作が失われないようにする。

## 形式ごとの変換手順

### プレーンテキストからMarkdown

1. 原文中の改行と、段落の区切りを見分ける。
2. 文書の題名を一つ決める。
3. 大きな話題ごとに節を分ける。
4. `・`、`○`、連番が、本当に一覧や手順を表しているか確認する。
5. 並列項目と、従属する条件や補足を分ける。
6. ラベルと本文の組を、見出し、リスト、表のどれにするか決める。
7. URLを、目的が分かるリンク文にする。
8. コード、パス、識別子を通常の文章と区別する。
9. 実際に表示し、見出し、リスト、コード、リンクを確認する。

### 紙面風の文書からHTML

1. 文字の大きさや太字ではなく、内容から見出しレベルを判断する。
2. 改ページを、そのままWeb上の節の区切りにしない。
3. 位置合わせ用の表を、段落、リスト、CSSレイアウトに置き換える。
4. 各ページに繰り返されるヘッダーやフッターを、本文から分ける。
5. 脚注を、本文から参照できる注記にする。
6. 図表に、必要なキャプション、見出し、代替説明を付ける。
7. DOMの順序と見出しの階層を確認する。

### MarkdownからHTML

1. 使用しているMarkdownの種類を特定する。
2. 拡張構文が、想定したHTMLになるか確認する。
3. 見出しレベル、リンク、画像の代替テキストを確認する。
4. Markdownの表で見出し関係が不足する場合は、HTMLで補う。
5. callout、脚注、Mermaidなどが表示されない場合の代替を確認する。
6. ページ全体を作る場合は、`lang="ja"`、`<title>`、`<main>` などを補う。

### HTMLからMarkdown

先に、Markdownでは同じ意味を表しにくい要素を特定する。

- 説明リスト
- 複雑な表
- 図とキャプション
- 振り仮名
- 折りたたみ
- 脚注
- ARIA属性で表していた関係
- フォームや対話要素

意味が失われる場合は、次のいずれかを選ぶ。

- HTMLの埋め込みを残す。
- 見出し付きの文章へ展開する。
- 変換できない点を注記する。

## 変換後に確認すること

### 内容

- 元の事実、数値、日時、単位を変えていないか。
- 条件、例外、否定の範囲を落としていないか。
- 手順や出来事の順序を前後させていないか。
- 見出しと本文の対応関係を変えていないか。
- 引用の範囲と出典を保っているか。
- リンク先、コード、コマンド、パス、識別子を変えていないか。

### 構造

- 最上位の見出しが文書の主題を示しているか。
- 見出しレベルを飛ばしていないか。
- 同じ階層の項目が並列になっているか。
- 条件、例外、例が、対応する上位項目の下にあるか。
- 表が、同じ軸で比較するデータになっているか。

### アクセシビリティ

- HTMLの主な言語を設定しているか。
- DOMの順序が、論理的な読み順や読み上げ順と一致しているか。
- 見出し、リスト、表、リンク、ボタンを適切な要素で表しているか。
- 色や位置だけで意味を伝えていないか。
- 画像に適切な代替テキストがあるか。
- 拡大や狭い画面でも情報が失われないか。

### 互換性

- Markdownの拡張構文を出力先が扱えるか。
- HTMLの埋め込みが許可されているか。
- 相対リンク、画像のパス、アンカーが有効か。
- コードフェンスと特殊文字が正しく閉じられ、必要な箇所でエスケープされているか。
