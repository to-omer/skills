# 文書の構成と情報の階層

この文書では、文章全体の組み立て方を扱う。文や語句を直す前に、読者、目的、情報の順序、見出し、段落、リストの関係を整える。

## 読者と目的を具体的にする

「一般向け」「初心者向け」だけでは、構成を決める材料として不十分である。次の点を具体的にする。

- 読者が知りたいこと
- 読者がすでに知っていること
- 読者が誤解しやすいこと
- 読者が文書を読む場面
  - 急いでいる、作業中、スマートフォンで読む、検索結果から来る、印刷して使うなど。
- 読後に行う判断や作業
- 誤読した場合に起こる問題

読者が複数いる場合は、全員向けの説明を一つの長い本文に混ぜ込まない。

1. 全員に共通する要点を先に示す。
2. 読者ごとの条件や手順は、別の節に分ける。
3. 必要な説明の詳しさが大きく異なる場合は、別ページや別文書にする。

## 文書に残す情報を選ぶ

本文には、読者が内容を理解し、判断し、行動するために必要な情報を置く。

### 先に置く情報

次の情報は、該当する場合、冒頭または早い位置に置く。

- 結論や変更点
- 対象者
- 影響
- 必要な対応
- 期限
- 安全、権利、料金、取り消せない操作に関する注意

### 後ろへ回せる情報

次の情報は、要点の理解に必要でなければ後ろへ移す。

- 詳しい経緯
- 補足的な根拠
- 一部の読者だけが使う例
- 参照資料
- 用語の詳しい解説

### 本文から分ける情報

次の情報は、現在採用している内容と同じ本文に混ぜない。

- 作成途中の考え
- 採用しなかった案
- 古い手順や廃止済みの仕様
- 前版との差分
- 内部向けの検討メモ

必要であれば、「変更履歴」「検討記録」「廃止した手順」などの節や別ファイルに分ける。

読者の判断や作業に不要な固有名、識別子、数値、時刻は、記録を目的とする文書を除き、本文に無理に残さない。

## 情報を並べる順序を決める

文書ごとに、情報を並べる基本の順序を一つ選ぶ。

- 重要なものから並べる。
- 読者が作業する順に並べる。
- 時系列に並べる。
- 原因から結果へ並べる。
- 全体を示してから部分へ進む。
- 読者が知っていることから、新しいことへ進む。
- 原則を示してから、条件と例外を示す。
- 問題を示してから、解決方法を示す。
- 同じ比較軸に沿って候補を並べる。

一つの節の途中で、並べ方を不用意に変えない。複数の順序が必要な場合は、節を分ける。

例:

- 文書の冒頭は、重要な情報から並べる。
- 手順の節は、操作する順に並べる。
- 障害の経緯は、時系列に並べる。

## タイトルと冒頭を書く

### タイトル

タイトルは、一覧や検索結果でも文書を見分けられるようにする。

必要に応じて、次の情報を含める。

- 主題
- 文書の種類
- 対象
- 日付や期間
- 影響や目的

例:

- 弱い: `お知らせ`
- 改善: `9月12日の点検によるファイルアップロード停止のお知らせ`
- 弱い: `設定について`
- 改善: `通知メールを停止する設定方法`

タイトルだけで結論をすべて言い切る必要はない。何についての文書かを示し、本文の冒頭で要点を伝える。

### 冒頭

冒頭では、読者が本文を読む必要があるか判断できるようにする。

文書の種類に応じて、次のうち重要なものを短く示す。

- 何が起きるか
- 誰に関係するか
- どのような影響があるか
- 何をする必要があるか
- いつまでか

挨拶、謝辞、組織内の経緯を長く書いてから要点を出さない。

## 見出しで文書の骨組みを示す

見出しには、その節で扱う対象か、読者が探す問いを書く。

### 内容が分かる見出しにする

次のような見出しは、単独では内容が分からない。

- `概要`
- `詳細`
- `重要なポイント`
- `3つの観点`
- `その他`

文書内での役割が明らかになるように具体化する。

- `停止する機能`
- `申請に必要な書類`
- `保存期間を過ぎたデータの扱い`
- `申請後に内容を変更する方法`

### 同じ階層の見出しをそろえる

同じ階層の見出しは、同じ基準で分類し、細かさもそろえる。

悪い例:

```markdown
## 申請方法
## 2026年4月1日から変更されます
## 問い合わせ先
```

「申請方法」と「問い合わせ先」は節で扱う対象だが、「2026年4月1日から変更されます」は結論文であり、並び方がそろっていない。

改善例:

```markdown
## 変更日
## 申請方法
## 問い合わせ先
```

各節の冒頭で、変更日や手順の要点を説明する。

### 見出しの階層を飛ばさない

上位の節の中に下位の節を置くときは、見出しレベルを一段ずつ下げる。

```markdown
# 利用申請

## 申請方法

### 必要な書類

### 申請の手順
```

`##` の直下に `####` を置かない。見た目の大きさではなく、内容の親子関係に合わせて見出しレベルを選ぶ。

### 見出しを増やしすぎない

短い段落ごとに見出しを置くと、話のまとまりが細切れになる。複数の段落が同じ問いに答える場合は、一つの節にまとめる。

## 従属する情報を正しく字下げする

リストでは、同じ階層に並ぶ項目だけを同じ字下げにする。

### 並列と従属を区別する

次の情報は、関係する上位項目の下に置く。

- 上位項目の理由
- 上位項目にだけ適用される条件
- 上位項目の例外
- 上位項目の具体例
- 上位項目を実行するための下位手順

悪い例:

```markdown
- 申請書を提出する。
- 管理者の承認が必要です。
- 緊急時は事後承認でも構いません。
- 本人確認書類を添付する。
```

この並びでは、承認と例外がどの項目に関係するか分かりにくい。

原文だけで適用先を判断できない場合は、字下げする前に確認する。管理者の承認と事後承認の例外が、申請書の提出にだけ関係すると確認できている場合は、次のように書く。

```markdown
- 申請書を提出する。
  - 管理者の承認が必要です。
  - 緊急時に限り、事後承認でも構いません。
- 本人確認書類を添付する。
```

「管理者の承認」が申請全体にかかる場合は、リストの前に独立した条件として書く。

```markdown
申請には、管理者の承認が必要です。緊急時に限り、事後承認でも構いません。

提出するものは次のとおりです。

- 申請書
- 本人確認書類
```

字下げは見た目を整えるためではなく、どの項目に属する情報かを示すために使う。

### 深い入れ子を避ける

三段以上の入れ子は、関係を追いにくくなる。次のいずれかを検討する。

- 小見出しに分ける。
- 条件ごとに節を分ける。
- 判断表にする。
- 手順と補足を別にする。

## 段落ごとに一つの話題を扱う

一つの段落では、読者にとって一つのまとまりとなる話題を扱う。

### 要点を早い位置に置く

実用文では、段落の冒頭か、できるだけ早い位置で要点を示す。その後に、必要な説明を続ける。

- 理由
- 根拠
- 条件
- 例
- 例外
- 読者への影響

例:

> バックアップは最長7日間保存されます。ただし、保存容量が50GBを超えると、7日を待たずに古いバックアップから削除されます。7日を超えて保存する必要がある場合は、外部の保存先へコピーしてください。

最初の文で原則を示し、次の文で条件と例外を説明し、最後の文で必要な行動を示している。

### 段落を分ける位置

次のいずれかが変わるところで、段落を分けることを検討する。

- 話題
- 主体
- 時点
- 視点
- 原則と例外
- 説明と手順
- 主張と具体例

ただし、短い関連文を機械的に一文ずつ別段落へ分けない。

### 段落どうしの関係を示す

読者が関係を取り違えそうな場合は、接続表現を使う。

| 関係 | 表現例 |
|---|---|
| 原因と結果 | そのため、したがって、〜ので |
| 条件 | 〜の場合、〜のとき、ただし |
| 対比 | 一方、これに対して、ただし |
| 追加 | また、さらに |
| 例 | 例えば、具体的には |
| 言い換え | つまり、ここでいう〜とは |
| 時系列 | まず、次に、完了後 |

接続語を増やすこと自体を目的にしない。関係が明らかな場合は、無理に付け足さない。

## 文書の種類に合う構成を選ぶ

以下は構成例であり、すべての項目を必ず使う必要はない。

### 告知、障害、変更

1. 何が起きるか
2. 誰に影響するか
3. いつ起きるか
4. 読者に必要な対応
5. 詳細と問い合わせ先

### 依頼、承認

1. 依頼すること
2. 期限
3. 完了の条件
4. 必要な理由
5. 手順と資料
6. 問い合わせ先

### 手順書

1. 手順の目的と完了の確認方法
2. 対象者
3. 前提条件と必要なもの
4. 実行する手順
5. 完了を確認する方法
6. 失敗した場合の確認と復旧
7. 関連情報

### トラブルシューティング

1. 症状
2. 影響する範囲
3. 最初に確認すること
4. 原因ごとの対処
5. 解消したか確認する方法
6. 解消しない場合の連絡先

### 説明、解説

1. 結論または定義
2. なぜ必要か
3. 仕組みや理由
4. 具体例
5. 適用できる範囲と限界
6. 関連情報

### 比較、選定

1. 比較する目的
2. 判断基準
3. 同じ基準による比較
4. 各候補の長所と制約
5. 推奨する候補と、その前提
6. 詳細情報

### 報告、インシデント

1. 要約
2. 影響
3. 現在の状態
4. 時系列
5. 原因
   - 確認済みの事実と未確定の推測を分ける。
6. 実施した対応
7. 今後の対応と次回更新

### 規程、ポリシー

1. 目的
2. 適用範囲
3. 原則
4. 義務と禁止
5. 条件と例外
6. 必要な手続き
7. 責任者と問い合わせ先

正式な文言を保つ必要がある場合は、平易な説明を併記し、正式文言を置き換えない。

### FAQ

1. 読者が実際に抱く質問
2. 直接の回答
3. 条件と例外
4. 必要な手順
5. 関連する質問

質問の直後に答えを書く。回答の前に長い背景説明を置かない。

## リスト、表、チェックリストを使い分ける

### 箇条書き

箇条書きは、次の目的に使う。

- 同じ種類の項目を並べる。
- 必要な条件や持ち物を、漏れなく確認する。
- 各項目を独立して拾い読みできるようにする。

リストの前に、何を並べるのか分かる導入文を置く。

```markdown
申請には、次の書類が必要です。

- 申請書
- 本人確認書類
- 在籍証明書
```

### 番号付きリスト

次の場合だけ番号を使う。

- 実行する順番がある。
- 優先順位がある。
- 項目数そのものに意味がある。
- 後から番号で参照する。

単なる並列項目には、番号を付けない。見出しへ手で通し番号を付ける場合も、手順を示したり後から参照したりするために番号が必要か確認する。

### チェックリスト

チェックリストは、完了と未完了を区別する作業や確認に使う。

説明、長所、参考情報をチェックリストにしない。

### 表

表は、同じ項目を同じ軸で比べる場合に使う。

表に向いているのは、次のような内容である。

- 料金、日付、上限、対応状況などの短い値
- 複数プランの同じ機能
- 条件ごとの結果

表に向いていないのは、次のような内容である。

- セル内に複数段落が必要な説明
- 項目ごとに比較軸が異なる内容
- 原因と結果を説明する文章
- 手順の細かな分岐

表が横に長くなる場合や、セルの文章が長い場合は、候補ごとの節や見出し付きリストに分ける。

## 注記、補足、警告を本文と区別する

注記には、内容に合うラベルを付ける。

- 補足
- 注意
- 警告
- 例
- 前提

重要な条件や例外を、目立ちにくい「補足」に移さない。

警告には、次の3点を示す。

1. 何が危険か。
2. 何が起きるか。
3. どう避けるか。

例:

> **警告:** この操作を実行すると、保存済みのデータを復元できません。実行前にバックアップを作成してください。

## 構成の最終確認

- タイトルで主題を判断できるか。
- 冒頭に、結論、影響、必要な対応があるか。
- 読者に不要な作成過程や古い情報が混ざっていないか。
- 見出しが節の内容を具体的に示しているか。
- 同じ階層の見出しとリスト項目が、同じ基準で分けられ、細かさもそろっているか。
- 条件、例外、理由、例が、対応する上位項目の下に置かれているか。
- 見出しやリストの入れ子が深すぎないか。
- 一つの段落で複数の話題を扱っていないか。
- 同じ主張を、見出し、冒頭文、段落末で繰り返していないか。
- 表を使う箇所と、リストや節に分ける箇所を使い分けているか。
