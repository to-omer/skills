# 改善例

例文では、表面上の短さだけでなく、意味、構成、情報の親子関係、自然な日本語を確認する。

## 直訳調の日本語を直す

### 改善前

> この工程では意味保存を行い、手順の順序を崩さず、義務の強さを壊さないことが重要です。

### 問題

- `意味保存` は助詞を省いた複合語で、本文として硬く不自然である。
- `順序を崩す` と `強さを壊す` は、動詞と目的語の組み合わせが不自然である。
- `重要です` だけでは、何を確認するのか具体的でない。

### 改善後

> この作業では、原文の意味を変えないでください。手順を前後させず、義務や推奨の度合いも変えないでください。

## 助詞の抜けと名詞の連続を直す

### 改善前

> 顧客申請内容確認結果通知を実施します。

### 改善後

> 顧客の申請内容を確認し、その結果を通知します。

名詞の関係を助詞で示し、`確認` と `通知` を動詞で書いている。

## 告知では影響と対応を先に書く

### 改善前

> 平素より本サービスをご利用いただき、誠にありがとうございます。このたび、より安定したサービス提供を目的とした設備点検を実施させていただくこととなりました。点検に伴い、9月12日午前2時から午前4時にかけて、ファイルのアップロード機能を停止させていただきます。すでにアップロードされたファイルの閲覧およびダウンロードは可能です。停止時間中にファイルを登録する必要がある場合は、午前2時までに操作を完了してください。作業状況により終了時刻が前後する場合があります。

### 改善後

```markdown
# 9月12日2:00からファイルのアップロードを停止します

設備点検のため、9月12日2:00から4:00ごろまで、ファイルをアップロードできません。停止時間中にファイルを登録する必要がある場合は、2:00までにアップロードを完了してください。

## 停止する機能

停止するのは、ファイルのアップロードです。

## 停止しない機能

- アップロード済みファイルの閲覧
- アップロード済みファイルのダウンロード

## 終了予定

作業状況により、終了時刻が4:00より早まる、または遅れる場合があります。
```

挨拶と経緯を短くし、日時、影響、必要な対応を先に示している。終了時刻が確定ではないことも残している。

## 短い文どうしの関係を補う

### 改善前

> バックアップは7日間保存されます。容量上限は50GBです。上限を超えると古いバックアップから削除されます。長期保存が必要なら外部へコピーしてください。

文は短いが、7日間の保存と50GBの上限の関係が分かりにくい。

### 改善後

> バックアップは最長7日間保存されます。ただし、保存容量が50GBを超えると、7日を待たずに古いバックアップから削除されます。7日を超えて保存する必要がある場合は、外部の保存先へコピーしてください。

`最長` と `ただし` を補い、容量を超えた場合は保存期間が短くなることを明示している。

## 従属する情報を字下げする

### 改善前

```markdown
申請方法は次のとおりです。

- 通常申請
- 上長の事前承認が必要です。
- 緊急時は事後承認でも構いません。
- 緊急申請
- 理由を記入してください。
```

### 問題

同じ階層に、申請の種類、条件、例外、必要事項が混ざっている。どの条件がどの申請にかかるか分からない。

### 改善後

```markdown
申請方法は次のとおりです。

- 通常申請
  - 上長の事前承認が必要です。
- 緊急申請
  - 緊急申請を選んだ理由を記入してください。

> **要確認:** 事後承認を認める対象は、原文だけでは特定できません。確認後、該当する申請方法の下へ置いてください。
```

確実に分かる条件と必要事項だけを、対応する申請方法の下へ置いている。適用先が分からない例外は、推測で字下げしていない。

## リスト全体にかかる条件は前に出す

### 改善前

```markdown
提出するものは次のとおりです。

- 申請書
  - 管理者の承認が必要です。
- 本人確認書類
```

管理者の承認が申請全体に必要である場合、この字下げでは申請書だけの条件に見える。

### 改善後

```markdown
申請には、管理者の承認が必要です。

提出するものは次のとおりです。

- 申請書
- 本人確認書類
```

## 見出しの分類をそろえる

### 改善前

```markdown
## 申請方法
## 2026年4月1日から変更されます
## 問い合わせ先
```

### 改善後

```markdown
## 変更日
## 申請方法
## 問い合わせ先
```

本文の冒頭で、`2026年4月1日から変更します` と説明する。見出しには節で扱う対象を書き、同じ階層の見出しの分け方をそろえている。

## 曖昧な修飾を勝手に決めない

### 原文

> 広報部から送られた承認済みの画像を法務部が確認した。

この文から確実に分かるのは、次の二点である。

- 画像は広報部から送られた。
- 法務部が画像を確認した。

誰が画像を承認したかは分からない。

### 不適切な改稿

> 法務部は、広報部が承認した画像を確認した。

広報部が承認したと決めている。

### 確認できないまま整える場合

> 法務部は、広報部から送られた承認済みの画像を確認した。画像を承認した部署は、原文からは分からない。

## 手順、完了条件、失敗時の対応を分ける

### 改善前

> 管理者アカウントでログインして設定の通知画面を開き、Webhook URLを入力後に保存し、テスト送信を行って成功と表示されたら完了です。失敗したときはURLとファイアウォールを確認してください。

### 改善後

```markdown
# Webhook URLを登録する

## 前提

管理者アカウントでログインしてください。

## 手順

1. **設定** から **通知** を開きます。
2. **Webhook URL** にURLを入力します。
3. **保存** を選びます。
4. テスト送信を実行します。

`成功` と表示されたら、登録は完了です。

## テスト送信に失敗した場合

次の項目を確認してください。

- 入力したURLが正しいか。
- ファイアウォールが通信を遮断していないか。
```

前提、操作、完了の確認、失敗時の確認を分けている。

## 比較できる情報だけを表にする

### 改善前

> Basicプランは月額800円で30日保存、メールサポートあり。Proプランは月額2,000円で365日保存でき、メールと電話のサポートがあります。

### 改善後

| 項目 | Basic | Pro |
|---|---:|---:|
| 月額料金 | 800円 | 2,000円 |
| 保存期間 | 30日 | 365日 |
| メールサポート | あり | あり |

料金が税込か税別か分からない場合は、推測で表に追加しない。Basicプランの電話サポートも、原文に記載がないため「なし」と断定しない。

## 条件の組み合わせは判断表にする

### 原文

> 申請額が10万円以上の場合は部長の承認が必要です。ただし、緊急購入であり、情報システム部が申請する場合にはCIOの承認が必要です。10万円未満は課長が承認します。

### 判断表

| 申請額 | 緊急購入 | 申請部門 | 承認者 |
|---|---|---|---|
| 10万円未満 | いいえ | 問わない | 課長 |
| 10万円未満 | はい | 情報システム部以外 | 課長 |
| 10万円未満 | はい | 情報システム部 | 要確認 |
| 10万円以上 | いいえ | 問わない | 部長 |
| 10万円以上 | はい | 情報システム部以外 | 部長 |
| 10万円以上 | はい | 情報システム部 | CIO |

### 確認事項

原文からは、10万円未満の緊急購入を情報システム部が申請する場合にもCIOの承認が必要か確定できない。表へ変換する前に、規則の適用範囲を確認する。

## 要約では対象範囲と未確認事項を残す

### 原文

> 試験運用では処理時間が平均18%短縮された。ただし、測定対象は画像ファイルのみで、参加者は社内の熟練者12人だった。文書ファイルを含む一般利用者で同じ効果が得られるかは未検証である。正式導入は、追加試験の結果を踏まえて判断する予定である。

### 不適切な要約

> 新機能により処理時間が18%短縮されるため、正式導入する。

平均値を一般化し、対象範囲と未確認事項を削り、正式導入が未決定であることも変えている。

### 適切な要約

> 社内の熟練者12人が画像ファイルを処理した試験では、平均処理時間が18%短縮された。一般利用者や文書ファイルでの効果は未確認であり、正式導入は追加試験後に判断する予定である。

## 同じ概念の呼び方をそろえる

### 改善前

> 利用者はワークスペースを作成できます。作成した作業領域にはメンバーを追加できます。このスペースは後から削除できます。

### 改善後

> 利用者はワークスペースを作成できます。ワークスペースにはメンバーを追加できます。また、ワークスペースは後から削除できます。

技術文書では、表現の単調さを避けることより、対象を正確に指すことを優先する。

## Markdownでは見た目ではなく役割を示す

### 不適切な例

```markdown
**申請方法**  
まずフォームを開きます。  
次に氏名を書きます。  
最後に送信します。
```

太字と強制改行で見た目を作っているが、節と手順としては分かりにくい。

### 改善例

```markdown
## 申請方法

1. 申請フォームを開きます。
2. 氏名を入力します。
3. **送信** を選びます。
```

## HTMLでは表の関係を要素で示す

### 不適切な例

```html
<div class="row"><b>項目</b> 基本 上位</div>
<div class="row"><b>保存期間</b> 30日 365日</div>
```

CSSが適用されなければ値の対応関係が分からず、支援技術も行見出しと列見出しの関係を読み取れない。

### 改善例

```html
<table>
  <caption>プラン別のログ保存期間</caption>
  <thead>
    <tr>
      <th scope="col">項目</th>
      <th scope="col">基本プラン</th>
      <th scope="col">上位プラン</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">保存期間</th>
      <td>30日</td>
      <td>365日</td>
    </tr>
  </tbody>
</table>
```

## 読みやすく見えても行ってはいけない変更

- `提出しなければならない` を `提出してください` に変え、義務の度合いを曖昧にする。
- `最大10件` を `10件` に変え、上限を固定値のように書く。
- `原因である可能性がある` を `原因である` に変える。
- 長い例外を、流れをよくするためだけに削る。
- 曖昧な主体を、文脈から推測して特定する。
- 複雑な条件を短い文に分けるだけで、条件と結論の対応関係を分かりにくくする。
- 見出しを太字へ変え、見た目だけを保つ。
- 一つの項目にだけ適用される例外を、同じ階層の別項目として並べる。
