# 短文と階層の改稿例

- 以下は、構成を比べるための作例
  - 手続き・報告・道具の設定は架空の材料であり、条件は各例の中だけに適用する
  - 実際の原稿では、その原稿の事実と条件を保つ

## 1. 親が示した範囲へ、子の内容を合わせる

ゲームを前後に二つ並べる例で、次の規則を説明する。

### 分類の軸が混ざった形

```markdown
- 一手番には、前か後ろの一方で指す
  - 前で指す場合：前を進め、後ろを指定局面へ戻す
  - 後ろで指す場合：後ろだけを進める
  - 補足：前が終わった後は、後ろだけを遊ぶ
```

### 操作の二択と、終了後の扱いを分ける

```markdown
- 一手番には、前か後ろの一方で指す
  - 前で指す場合：前を進め、後ろを指定局面へ戻す
  - 後ろで指す場合：後ろだけを進める
- 前が終わった後は、後ろだけを遊ぶ
```

- 最初の二項目は、どちらで指すかという選択肢
- 三項目目は、前が終わった状態の扱い
  - 「補足」と付けても所属は直らないため、列挙の外へ移した

## 2. 親と子を合わせて、関係が分かるようにする

### 親で関係と範囲を示す

```markdown
- 次の二条件を両方満たす場合に申請できる
  - 利用者登録が完了している
  - 未返却の機器がない
```

- 親が「二条件を両方」と示しているので、子に「条件：」を繰り返す必要はない
- 親項目だけ読んでも、無条件に申請できるとは受け取られない

### 一つの操作に、目的と例を付ける

材料：申請に使った添付ファイルは、審査資料を後から照合するために保存する。添付資料には、例えば見積書がある。

```markdown
- 申請に使った添付ファイルを保存する
  - 審査に使った資料を後から照合するため
  - 資料の例：見積書
```

- 同じ保存操作の下に、目的と資料の例を置いた
  - 役割の違いが分かれば、同じ親の下に置ける
  - 役割が違うことだけを理由に、説明を別の場所へ散らさない
- 「〜ため」で目的が分かるので、さらに「目的：」を付けなくてよい
- 「資料の例」で、見積書が保存する資料の例だと示した

### 分類ラベルは、説明する場所を案内する

材料：予約日時は、利用日の前日17時まで無料で変更できる。それ以降は変更できない。

```markdown
- 予約日時の変更条件
  - 利用日の前日17時までなら、無料で変更できる
  - それ以降は変更できない
```

- 親項目は条件を読む場所を示しており、無条件に変更できるとは述べていない
  - 親項目で「無料で変更できる」と主張する形なら、期限もそこに残す

## 3. 次の工程と、操作の効果を分ける

材料：計算を実行すると結果一覧が表示される。その一覧から一件選び、詳細を開く。

```markdown
1. 計算を実行する
   - 実行後、結果一覧が表示される
2. 結果一覧から一件選び、詳細を開く
```

- 一覧の表示は、最初の操作で起こること
  - 次に行う操作ではないため、最初の工程の下に置ける
- 詳細を開くことは、次に行う独立した工程
  - 同じ階層で番号を続ける

工程を詳しく分けるなら、内訳を下に置ける。

```markdown
1. 申請内容を確認する
   1. 氏名と連絡先を確認する
   2. 金額と添付資料を確認する
2. 確認が済んだら申請を送信する
```

- 内側の二工程は、「申請内容を確認する」ための内訳
- 時間が進むだけなら下げず、一工程の内訳ならその下に置く

共通の条件がある場合も、内訳の全体に掛かるように書く。

```markdown
- 入力内容に問題がない場合は、次の順で提出する
  1. 添付資料を登録する
  2. 申請を送信する
```

- 親から二つの操作へ条件が掛かるので、各操作へ繰り返す必要はない
  - 一番目の操作だけに条件を付けると、二番目が無条件にも読める

## 4. 複数の前提を、結論へつなぐ

材料：A案もB案もCSVを出力できる。今回比べるのは、CSVを出力できるという要件を満たすかどうかだけである。

### 結論を、最後の前提だけの子にしない

```markdown
- A案はCSVを出力できる
- B案もCSVを出力できる
  - したがって、CSV出力の可否では両案とも要件を満たす
```

### 必要な前提を、結論の下へそろえる

```markdown
- CSV出力の可否では、両案とも要件を満たす
  - A案はCSVを出力できる
  - B案もCSVを出力できる
```

- どの点で両案が要件を満たすかを、親項目に残した
- 前提を読んでから結論へ進む方がよい文脈なら、二つの前提の後に結論を置いてもよい

## 5. 短文化や接続の追加で、言える範囲を変えない

材料：設定変更後、12人の自己評価の平均は2.8から3.6になった。個人別の変化は記録していない。比較対象がなく、設定変更が原因かも調べていない。

```markdown
- 設定変更後、12人の自己評価の平均は2.8から3.6へ上がった
- 全員が改善したかは分からない
  - 個人別の変化を記録していないため
- 設定変更が原因かは分からない
  - 比較対象がなく、原因を調べていないため
```

- 「平均」を親項目に残し、全員の改善へ広げていない
- 設定変更後の報告と、原因の特定を分けた
  - 「設定を変えたため、平均が上がった」とは書けない
- 短くしても、結論を変える限定は残す
  - 「次の二条件を両方」のような組み合わせ方も、単なる「条件」に省略しない

## 6. 名前を並べるだけでなく、短文で説明をつなぐ

### 定義の動機が伝わらない形

```markdown
- 一本道
- 分岐
- 手数
- 指標
```

### 対比と、新しい問いをつなぐ

この作例では、どの道筋も有限の手数で終わるゲームを考える。

```markdown
- 一本道と、分岐があるゲームを比べる
  - 一本道なら、終了までの手数は最初から決まる
  - 一方、分岐があると、選ぶ手によって終了までの手数が変わることがある
- そこで、勝敗に加え、勝ちを保って何手で決着できるかを調べる
```

- 何が違い、何を調べたいかを文で示した
  - この後、必要な比較例を経て、手数を表す量の定義へ進める
- 短い条件と一連の操作は、同じ項目でも読める
  - 「入力内容に問題がなければ、添付資料を登録して申請を送信する」
  - 「入力に問題なし」「資料登録」「送信」だけに分けると、条件との関係が弱くなる

## 7. 項目を増やす前に、内容と置き場所を見直す

- 規則の説明に残す
  - 一手番の操作と終了条件
  - 必要な設定と、違いが分かる最初の例
- 必要になる場所へ移す
  - 勝敗の公式：判定に使う数値を説明した後
  - 原論文との記法の違い：原典を読むための注記
- 役割のない重複は整理する
  - 見出し・導入・親項目の同じ案内を減らす
  - 解説と比較表のように、読む用途が違う再掲は残せる
- 説明の長さだけを理由に、補足へ移さない
  - 証明そのものを求められた場合は、その論証を本文でたどれるようにする
- 項目数だけでは、分けるかどうかを決めない
  - 明確に並列な六つの規則なら、六項目のまま比べられる
  - 三項目でも、親が示した問いや範囲から外れるものがあれば直す
