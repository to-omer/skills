# 読みやすい単一 HTML 文書を作る

## 目的

与えられた内容の意味と言語を保ち、原則として一つの `.html` ファイルへまとめる。文書としての読みやすさを先に設計し、UI、装飾、外部ライブラリは、読者に明確な利益がある場合だけ加える。

## 必ず守る要件

- 元の意味、言語、数値、条件、例外、引用、コードを保つ
- セマンティック HTML とレスポンシブ CSS を使う
- JavaScript は、内容の理解、探索、操作を実質的に改善する範囲だけ使う
- ページ固有の CSS、JavaScript、データ、簡単な画像やアイコンは、原則として HTML 内へ含める
- 固定テンプレートを押し付けず、内容、読者、利用状況から構造と見た目を決める
- 画像や図は、要求されている場合、または文章より明確に理解を助ける場合だけ使う
- 完了前に、内容、構造、表示、操作、依存関係を必ずレビューする

## 単一ファイル性と外部依存を分けて考える

「単一 HTML」は、納品する文書ファイルが一つであることを指す。外部 URL を一切参照しない「オフライン自己完結」とは別の要件である。

KaTeX、MathJax、構文強調、図表描画などの外部ライブラリが、正確さ、読みやすさ、アクセシビリティ、または表示の信頼性を明確に高め、標準 HTML・CSS・小さな埋め込み JavaScript だけでは同等の品質を得にくい場合は、CDN から利用してよい。単一ファイルであることだけを理由に禁止しない。

外部ライブラリを使う場合は、次を守る。

- 装飾や小さな便利機能だけを目的に導入しない
- 必要なライブラリだけに絞る
- 信頼できる配信元の、バージョンを固定した URL を使う
- 利用できる場合は Subresource Integrity と `crossorigin` を設定する
- 読み込みに失敗しても、中心内容へ到達できる代替表示を残す
- 依存先、目的、ネットワークを利用できない場合の影響を納品時に明示する
- 機密情報や個人情報を外部サービスへ送信しない

ユーザーがオフライン動作、閉域環境、長期保存、厳格な Content Security Policy などを求める場合は、外部依存を避ける。ライセンスと容量が許せば必要資産を埋め込み、難しい場合は依存しない表現へ切り替える。

ユーザーが複数ファイルや特定のホスティング構成を明示した場合は、その指定を優先する。

## 最初に作業範囲を確定する

### 形式変換だけの場合

内容、言語、意味上の読み順、見出しの階層、数値、条件、引用、コードを保持する。HTML に適した要素へ置き換えるための最小限の構造変更だけを行う。

### 内容編集も求められた場合

読みやすさのために構成や文章を編集できる。日本語を編集する場合は `japanese-readable-writing` Skill も適用し、同 Skill の作業種別と必須レビューに従う。

### 新規ページを作る場合

ユーザーが与えた情報と確認できる根拠を基に、必要な内容を組み立てる。見栄えを整えるために、存在しない実績、数値、引用、統計を加えない。

## 参照資料を照合する

すべての HTML 作成で、作業前に次の二つの reference を読み、必須レビューでは該当節を成果物へ照合する。

| 参照資料 | 主に照合する内容 | 主なレビュー段階 |
|---|---|---|
| [読みやすさとレイアウト](references/readability-and-layout.md) | 本文幅、読み列、余白、見出し、目次、リスト、表、数式、図、対話機能、レスポンシブ表示、印刷 | 第2〜5段階、第7段階 |
| [検証](references/validation.md) | 内容照合、ソース、依存関係、実ブラウザー、キーボード、実施記録 | 第1・2・4〜7段階 |

適用対象の reference を未読のままレビュー完了と扱わない。該当する要素がない場合も、成果物と依頼内容を確認し、追加する必要もないと判断してから対象外とする。

## 基本原則

### 文書を先に、インターフェースを後にする

最初に、主題、読み順、見出し、段落、表、数式、図を設計する。その後で、目次、検索、タブ、折り畳み、コピー機能などが本当に必要か判断する。

HTML らしさを示すためだけに、機能や装飾を増やさない。

### 主な読み列を守る

一般的な長文では、一つの主要な読み列を既定にする。固定サイドバーや複数カラムが本文を狭くする場合は使わない。

目次は、長い文書で移動を明確に助ける場合だけ付ける。中間的な画面幅で本文を圧迫するなら、本文上部、折り畳み、または通常フローへ置く。

### 意味を見た目へ依存させない

見出し、段落、リスト、表、リンク、ボタン、数式、図を、役割に合う要素と属性で表す。色、位置、太字、カードの形だけで階層や状態を伝えない。

## 作業手順

### 1. 内容と制約を整理する

次を確認する。

- 元の言語、主題、読者、目的
- 形式変換だけか、内容編集も含むか
- 必ず保持する見出し、数値、条件、引用、コード、リンク
- 出力先、画面、印刷、アクセシビリティ、対話機能の要件
- 単一ファイル、オフライン動作、外部ライブラリ、ファイル名などの制約

不足情報を推測で埋めない。

### 2. 文書構造を作る

`header`、`main`、`footer`、`nav`、`article`、`section` などを、内容上の役割に応じて使う。要素数を増やすこと自体を目的にしない。

見出しは内容の階層に合わせ、レベルを飛ばさない。DOM の順序を意味上の読み順と一致させ、CSS だけで見た目の順序を大きく入れ替えない。

### 3. 読みやすいレイアウトを設計する

安全な既定値は次のとおりである。

- 一つの主要な読み列
- 長すぎない本文幅
- 本文を追える行間と段落間隔
- 見出しの前後に、階層が分かる余白
- カードや囲みより、通常の段落と余白を中心にした構成
- 表とコードだけの局所的な横スクロール
- ページ全体に不要な横スクロールを発生させないレイアウト

内容に理由がある場合は、これらから外れてよい。具体的な判断は [読みやすさとレイアウト](references/readability-and-layout.md) に従う。

### 4. セマンティック HTML を書く

少なくとも次を含む完全な文書を作る。

- `<!doctype html>`
- 言語を示す `html[lang]`
- `meta charset`
- `meta name="viewport"`
- 内容を表す `title`
- 一つの主要な `main`
- 文書の主題を示す `h1`

リンクは移動、ボタンは操作に使う。入力にはラベルを付ける。表では、見出しセルとデータセルの関係を示す。画像の `alt` は、目的に応じて情報を伝えるか、装飾画像なら空にする。

### 5. レスポンシブ CSS を書く

ページ固有の CSS は HTML 内へ含める。固定幅で本文を狭い画面からはみ出させない。

- 本文、見出し、ラベルが自然に折り返すようにする
- 表とコードには、必要な場合だけ局所的な `overflow-x` を使う
- 固定・sticky 要素が本文やフォーカス対象を覆わないようにする
- 文字を拡大しても、内容や操作を失わないようにする
- 色だけに頼らず、十分なコントラストを確保する

標準フォントでも内容を読めるフォールバックを用意する。Web フォントは、必要な文字を正しく表示するか、判読性を明確に高める場合に限って使う。ブランド表現だけを理由に必須化しない。

### 6. JavaScript と外部ライブラリを判断する

まず、JavaScript なしでも中心内容を読める HTML を作る。検索、絞り込み、タブ、コピーなどが読者の負担を明確に減らす場合だけ JavaScript で強化する。

複雑な数式を正確に組版する KaTeX など、外部ライブラリの方が明らかに品質を高める場合は CDN を利用できる。簡単な機能のために大きなライブラリを導入しない。

対話機能では、キーボード操作、コントロールの名前、状態通知、フォーカス、JavaScript 無効時の中心内容を保つ。

### 7. 単一ファイル性と依存関係を整える

ページ固有の CSS、JavaScript、データ、簡単な画像やアイコンは、原則として HTML 内へ含める。外部ライブラリを使う場合も、納品物は一つの HTML にできる。

外部依存を選んだ理由、固定したバージョン、読み込み失敗時の表示、オフライン要件との整合を確認する。

### 8. 画像と図を判断する

画像や図を加える前に、次を一文で答える。

> この図は、読者のどの問いへ答え、文章よりどれだけ理解を短縮するか。

答えられない場合は使わない。本文と同じ内容を繰り返す画像、飾りだけの統計、意味の対応が不明な図を加えない。

図だけに重要情報を置かず、本文、キャプション、代替テキストでも要点を伝える。色だけで分類しない。

## 必須のレビュー工程

**すべての HTML 作成で、次の七段階を順番に実行する。短いページでも省略しない。** 利用できるツールが限られる場合も各段階で可能な確認を行い、実施できなかった確認を実施済みと扱わない。

各段階で指定された reference を開き、現在の成果物と該当規則を照合する。修正した場合は、その修正が影響する段階から第7段階までを再実行する。

1. **第1段階: 内容の保持と完全性**
   - [検証](references/validation.md) の「内容を照合する」を実行する
   - 日本語を編集した場合は `japanese-readable-writing` Skill のレビューも実行する
2. **第2段階: 文書構造と読み順**
   - [検証](references/validation.md) の「ソースを確認する」を照合する
   - [読みやすさとレイアウト](references/readability-and-layout.md) の読む仕事、主要な読み列、見出しと目次、形式に関する節を照合する
3. **第3段階: 視覚的な読みやすさ**
   - [読みやすさとレイアウト](references/readability-and-layout.md) の本文幅、タイポグラフィ、余白、形式、数式、図に関する節を照合する
4. **第4段階: レスポンシブ表示**
   - [読みやすさとレイアウト](references/readability-and-layout.md) の「レスポンシブ表示」を照合する
   - [検証](references/validation.md) の「実ブラウザーで確認する」を、利用可能な範囲で実行する
5. **第5段階: アクセシビリティと対話**
   - [読みやすさとレイアウト](references/readability-and-layout.md) の数式、図、色、対話機能に関する節を照合する
   - [検証](references/validation.md) の「キーボードと対話機能を確認する」を実行する
6. **第6段階: ソース、単一ファイル性、依存関係**
   - [検証](references/validation.md) の「ソースを確認する」と「単一ファイル性と依存関係を確認する」を実行する
7. **第7段階: 実表示と最終通読**
   - [検証](references/validation.md) の実ブラウザー確認、初見読者としての通読、実施記録に従う
   - [読みやすさとレイアウト](references/readability-and-layout.md) の該当する全節を最終的に照合する

図、対話機能、外部ライブラリ、印刷などがない場合も段階を省略しない。該当要素がないことと、追加する必要もないことを確認して対象外とする。

## 納品

ファイル出力が可能な環境では `.html` ファイルを作る。ファイルを作れない環境では、一つの完全な `html` コードブロックを返す。

ユーザーが複数ファイルを明示的に求めた場合だけ分割する。外部ライブラリを使った場合は、依存先、目的、オフライン時の影響を簡潔に伝える。確認結果を報告する場合は、実際に行った確認と、行えなかった確認を分けて書く。
